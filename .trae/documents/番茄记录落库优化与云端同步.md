# 番茄记录落库优化与云端同步

## Context（背景）

当前应用存在两个问题：

1. **后端每秒落库**：番茄钟运行期间，后端 `PomodoroManager` 的 `tick_once` 每秒调用 `db.persist_effective()` 写一次本地 SQLite（`src-tauri/src/pomodoro_manager.rs` 约 352-358 行）。需要改为仅在暂停/中断/完成等状态流转时落库。

2. **番茄记录从不入云端**：后端所有 `pomodoro_records` 写入只发生在本地 SQLite，从未同步到 Supabase 云端。前端 `createPomodoroRecord` 是未被调用的死代码，云端 `pomodoro_records` 表实际为空。而 `PlanSwiper.vue` 通过 `getRepository().countCompletedPomodoros` / `countOccurrencePomodoros`（云端优先）读取番茄计数，导致本地完成的番茄在 UI 上读不到。需要让后端写库与云端同步。

### 已确认的设计决策（用户拍板）

- **同步范围**：后端每次写库（开始 / 暂停 / 恢复 / 中断保存 / 完成）都同步，即 `running / paused / interrupted_saved / completed` 状态都同步到云端。
- **不回填历史**：仅向前同步，本次改动之后的新增/修改才同步，历史本地记录不做一次性回填。
- **同步方式**：事件驱动。后端每次写库成功后 `emit` 一条 `pomodoro_record_sync` 事件（携带记录全量快照），前端主窗口 `App.vue` 全局监听，调用 `getRepository().upsertPomodoroRecord()` 幂等 upsert 到云端（云端权威、本地静默镜像）。这样保持"前端唯一持有 Supabase 客户端、UI 只用 getRepository()"的既有架构，不在 Rust 侧重复实现云逻辑。

---

## 改动 1：移除每秒落库

- `src-tauri/src/pomodoro_manager.rs` 的 `tick_once`：删除 else 分支中每秒调用 `db.persist_effective(&id, eff)` 的逻辑。
- `src-tauri/src/pomodoro_db.rs`：删除不再使用的 `persist_effective` 函数。
- 结果：本地写库只发生在 `insert_running` / `update_transition`（暂停/恢复） / `update_interrupt_saved`（中断） / `update_completed`（完成），且这些函数均已写入 `effective_total_seconds`。
- **注意**：每秒的 `pomodoro_state_update` 事件广播必须保留——前端无本地计时器，倒计时完全依赖该事件。

## 改动 2：后端写库事件驱动同步到云端

### 后端

**`src-tauri/src/state.rs`**：新增可 `Serialize` 的结构体 `PomodoroRecordSync`（snake_case 字段，与前端同名类型一一对应）：

```rust
#[derive(Clone, Debug, Serialize)]
pub struct PomodoroRecordSync {
    pub id: String,
    pub task_id: String,
    pub occurrence_date: Option<String>,
    pub record_date: String,
    pub start_time: String,
    pub end_time: Option<String>,
    pub effective_total_seconds: u32,
    pub status: String,      // running | paused | interrupted_saved | completed | abandoned | interrupted(遗留)
    pub resume_count: u32,
    pub interrupt_duration_seconds: Option<u32>,
    pub reward_gold: u32,
}
```

**`src-tauri/src/pomodoro_db.rs`**：
- 删除 `persist_effective`。
- 新增 `load_record(id) -> Result<Option<PomodoroRecordSync>, String>`：按 id 读全量列，数值列沿用现有 `r.get::<_, i64>(n)? as u32` 的先例（参考 `load_active_record`），`status` 直接读 String 透传。

**`src-tauri/src/pomodoro_manager.rs`**：
- 新增自由函数 `emit_record_sync(db: &Db, app: &AppHandle, id: &str)`：`db.load_record(id)` 成功后 `app.emit("pomodoro_record_sync", rec)`，加载失败仅日志、不阻塞主流程。
- 在全部 6 处写库成功后调用（命令方法里用 `self.db` / `self.app`；tick 里用传入参数）：
  1. `start()` 恢复中断分支：`update_transition("running")` 之后
  2. `start()` 新建分支：`insert_running` 之后（需把 `id` 从锁块内提出）
  3. `pause()`：`update_transition("paused")` 之后
  4. `resume()`：`update_transition("running")` 之后
  5. `interrupt_save()`：`update_interrupt_saved` 之后
  6. `tick_once` 完成分支：`update_completed` 成功之后（把 `completed: bool` 改为 `completed_id: Option<String>`，仅落库成功才 emit 并置完成）
- `restore()` 不写库，无需同步。`abandoned` 只存在于内存、从不落库，无需同步路径。

### 前端

**`src/api/types.ts`**：
- 新增 `PomodoroRecordSync` 接口（status 用宽联合 `'running' | 'paused' | 'interrupted_saved' | 'completed' | 'abandoned' | 'interrupted'`，与 `PomodoroRecord.status` 相互独立，**不放宽** `PomodoroRecord.status` 以免牵连大量改动）。
- `TaskRepository` 接口新增 `upsertPomodoroRecord(input: PomodoroRecordSync): Promise<void>`。

**`src/api/pomodoro.ts`**：
- 导出 `PomodoroRecordSync` 类型。
- 新增 `onPomodoroRecordSync(handler)`：监听 `pomodoro_record_sync` 事件（复用 `listen`）。

**`src/api/cloudRepository.ts`**：实现云端 upsert：

```ts
async upsertPomodoroRecord(input: PomodoroRecordSync): Promise<void> {
  const { error } = await supabase.from('pomodoro_records').upsert(input, { onConflict: 'id' });
  if (error) throw error;
}
```

**`src/api/localRepository.ts`**：实现本地幂等 upsert（INSERT 分支 `created_at` 用 `CURRENT_TIMESTAMP` 兜底；ON CONFLICT(id) DO UPDATE 更新各列但不触碰 `created_at`）。

**`src/api/index.ts`**：`dualRepository` 新增 `upsertPomodoroRecord`（先云端，成功后再 `localWrite` 本地静默镜像），维持"云→本地"双写约定。

**`src/App.vue`**：`onMounted` 里新增 `onPomodoroRecordSync` 全局监听，fire-and-forget 调 `getRepository().upsertPomodoroRecord(payload).catch(...)` 并打错误日志；`onBeforeUnmount` 清理。主窗口关闭到托盘时 webview 仍存活（`lib.rs` 仅 `window.hide()`），监听不中断；`PetTimerWindow` 不监听该事件，不会重复 upsert。

## 前置核查

- 核实线上 Supabase `pomodoro_records` 表已含 `occurrence_date` 列（同步负载会携带该字段；缺失会导致云端 upsert 报错）。若缺失，在 Supabase SQL Editor 执行 `alter table pomodoro_records add column occurrence_date date;`。
- 顺手修正 `cloudRepository.ts` 头部注释里过期的建表 SQL（补 `occurrence_date` 列，避免后续误判）。

## 验证方法

1. 后端编译：`src-tauri` 下 `cargo check`。
2. 前端类型检查：`node_modules/.bin/vue-tsc.cmd --build --force`（沙箱环境避免直接 npm）。
3. 手动端到端（在 Tauri 运行）：
   - 开始番茄 → Supabase 查 `pomodoro_records`：出现 `status='running'` 记录。
   - 暂停 → 云端该行变 `paused`、`resume_count=1`；恢复 → `running`；中断保存 → `interrupted_saved` 且 `interrupt_duration_seconds`/`end_time` 有值。
   - 完成 → 云端变 `completed`、`reward_gold`/`end_time` 更新；回任务列表番茄计数能读到新完成数（修复前为空）。
   - 运行期间观察本地 plan.db 写频率：`effective_total_seconds` 不再每秒写入。
   - 主窗口收进托盘后（桌宠操作）完成一个番茄 → 云端仍能同步。

## 已知取舍（可接受，不处理）

- 用户直接退出应用（非完成/中断）时云端会遗留一条 `status='running'` 残行；计数只查 `completed` 不受影响，删任务"已执行"判定与本地一致。
- 事件驱动 + fire-and-forget：完成番茄后立即退出可能来不及写云，属固有取舍。
- `end_time` 在 resume 恢复时不清空，同步如实镜像本地既有行为。
- 移除每秒落库后，崩溃恢复精度回退到"最近一次状态流转"，可接受。
